# Claude와 Codex의 협업

이 사례에서 Claude Code는 작업을 지시하고 결과를 검증하는 오케스트레이터이며, Codex는 지시받은 범위를 구현합니다. 사람은 목표와 중요한 결정을 정하고 결과를 확인합니다.

1. **지시서**: Claude가 `docs/handoff/<작업 ID>.md`에 목적, 수정할 파일, 완료 조건, 금지 사항, 검증과 보고 형식을 적고 작업 브랜치를 준비합니다. [T0b 지시서](../handoff/T0b.md)가 예시입니다.
2. **실행**: 사용자가 Codex 창에 지시서를 따르라고 입력하거나, 사용자 승인 후 Claude가 `codex exec`로 실행합니다. Codex는 지정된 파일만 수정하고 커밋·push·브랜치 변경을 하지 않습니다.
3. **QC**: Claude가 완료 조건을 직접 확인하고 테스트합니다. 실행하지 않은 검증은 미검증으로 남깁니다. T0b에서는 점검 모드가 conda 환경의 Node를 찾지 못하는 문제가 발견됐습니다.
4. **수정과 재검증**: 실패한 명령과 오류 원문, 같은 원인으로 영향을 받을 수 있는 부분을 Codex에 전달합니다. Codex가 수정하면 Claude가 다시 검증합니다.
5. **기록**: Claude가 작업과 검증 결과를 기록하고 커밋·push합니다. 사용자가 PR 병합을 하거나 요청할 때만 병합합니다.

## 진행 현황 보기

`scripts/codex-run.sh`는 실행 시작·종료와 종료 코드를 별도 진행 폴더의 `PROGRESS.md`에 기록하고 로그와 최종 보고를 남깁니다. Codex가 단계별로 추가하는 GPT 행은 자기 보고이므로 완료 여부는 QC로 확인합니다. 스크립트 사용법은 파일의 첫 부분을 참고하세요.

## 브랜치와 push 안전장치

이 저장소는 `develop`에서 작업별 `feature/*` 브랜치를 만들고 `develop`으로 PR을 보냅니다. `master`는 배포용입니다. push할 때는 `git push origin feature/<이름>`처럼 브랜치를 명시하고, 그냥 `git push`는 쓰지 않습니다. 설정은 feature·bugfix push만 자동 허용하고 force push, 삭제, `develop`·`master` 직접 push를 거부하도록 구성했습니다. 패턴 기반 거부는 우회될 수 있으므로 GitHub 브랜치 보호도 권장됩니다. 비밀 정보는 저장소에 넣지 않습니다.
