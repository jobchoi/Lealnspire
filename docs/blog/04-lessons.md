# 실패를 다음 작업의 자산으로

개발 도구가 멈추거나 테스트가 실패하면 코드부터 고치고 싶어집니다. 하지만 Lealnspire의 기록에는 권한, 설정 형식, 테스트 환경처럼 코드 바깥에서 원인을 찾은 사례도 있습니다. 실패와 대응을 남겨 두면 다음에는 같은 문제를 더 빨리 구분할 수 있습니다.

## 403은 먼저 권한을 확인

클라우드 세션에서 GitHub 저장소로 push하려던 시도가 403 오류로 실패했습니다. 기록된 원인은 Claude GitHub 앱에 해당 저장소 권한이 없었던 것입니다. 권한 문제가 해결된 뒤 다시 push하고 GitHub Actions 결과를 확인했습니다.

이 사례가 모든 403의 원인을 설명하지는 않습니다. 다만 오류를 무시하거나 무작정 재시도하기 전에 요청 대상과 권한을 확인할 이유는 됩니다. 이 프로젝트에서는 필요한 권한을 AI가 스스로 넓히지 않고 사용자가 검토하도록 했습니다.

## 설정은 내용뿐 아니라 형식도

설정 파일 맨 앞에 `//` 주석이 있어 JSON 형식이 깨지고 설정 전체가 무시된 일이 있었습니다. 규칙을 적어 놓았다는 것과 도구가 그 규칙을 읽었다는 것은 다릅니다. 설정이 기대대로 동작하지 않으면 우선 해당 파일의 형식과 실제 적용 여부를 살펴볼 수 있습니다.

다른 사례는 브라우저였습니다. 프로젝트의 Playwright MCP는 별도의 브라우저 설치 명령을 사용합니다. 일반 브라우저가 설치돼 있다는 사실만으로 테스트에 필요한 브라우저까지 준비됐다고 판단할 수 없습니다. 이후 새 환경에서 E2E용 Chromium이 빠진 문제도 발견되어 setup이 설치와 존재 점검을 하도록 보강됐습니다.

## 멈춘 작업과 진행 기록

백그라운드에서 실행한 `codex exec`가 표준 입력을 기다리며 멈춘 사례도 있었습니다. 실행 스크립트는 입력을 닫아 이 문제에 대응했습니다.

```sh
codex exec ... < /dev/null
```

위의 `...`은 실제 작업 지시가 들어갈 자리입니다. 입력을 닫았다는 사실만으로 성공을 판단하지 않고 로그와 종료 코드도 확인합니다.

진행 기록에는 단계와 결과를 짧게 남겼습니다. 다만 작업자가 직접 쓴 진행 행은 자기 보고이므로, 완료 여부는 별도의 QC로 확인합니다.

> [스크린샷: 민감 정보를 가린 오류와 진행 기록의 예시 행]

실패를 자산으로 바꾸는 데 필요한 것은 화려한 분석이 아닙니다. 무엇을 실행했는지, 무엇이 실패했는지, 어떻게 수정했는지, 어디까지 재검증했는지를 다음 사람이 구분할 수 있게 쓰는 것입니다.
