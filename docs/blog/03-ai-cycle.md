# AI로 시작하는 첫 블록부터 아이언맨까지 #3 — 두 AI가 협업하는 한 사이클

한 AI가 만든 결과를 다른 AI가 확인하면 무엇이 달라질까요? Lealnspire의 T0b 환경 구성 작업에는 지시, 구현, 검증, 수정과 재검증이 한 바퀴 돌아간 기록이 있습니다. 두 도구를 사용했다는 사실보다 중요한 것은 각 단계의 책임과 확인 결과를 남긴 방식입니다.

## 1. 완료 조건을 먼저 쓰기

Claude는 작업 지시서에 목적, 만들거나 수정할 파일, 완료 조건, 금지 사항, 검증과 보고 형식을 적었습니다. Codex는 지정된 범위에서 구현하며 커밋이나 브랜치 변경은 하지 않는 역할을 맡았습니다. 사람은 목표와 작업 방식을 결정했습니다.

이렇게 쓰면 “잘 만들어 줘”보다 결과를 평가하기 쉽습니다. 예를 들어 환경 구성 스크립트는 설치를 수행하는 것뿐 아니라 현재 상태를 점검하고, 운영체제별로 실제 확인한 범위를 보고해야 했습니다.

> [스크린샷: 개인정보를 가린 T0b 지시서의 완료 조건]

## 2. 구현과 자기 보고

Codex는 셸 스크립트와 PowerShell 스크립트, 사용 안내를 작성했습니다. 보고에는 요구사항 하나를 충족하지 못했고 나머지 대부분도 검증하지 못했다고 명시했습니다. 작성자의 자기 점검은 출발점이지만, 실행하지 않은 검증을 통과로 바꾸지는 않습니다.

작업을 나눠 맡길 때는 AI에게 수정 범위뿐 아니라 검증이 불가능한 경우의 보고 방법도 알려 줄 수 있습니다. 이 저장소는 실행하지 않은 항목에 “미검증”과 이유를 남기도록 정했습니다.

## 3. 독립 QC와 수정

Claude의 검증에서 Linux 전체 실행과 Windows PowerShell 5.1 점검 모드는 동작했습니다. 그러나 점검 모드가 conda 환경의 Node를 찾지 못하는 문제가 발견됐습니다. Claude가 수정 지시를 전달하고 Codex가 고친 뒤, 재검증에서 점검 항목이 모두 정상으로 확인됐습니다. 이는 점검 모드에 대한 결과입니다.

수정 요청에는 실패한 명령과 오류 메시지 원문, 같은 원인으로 영향을 받을 만한 항목을 함께 전달하는 것이 규칙입니다. 이렇게 하면 수정자가 첫 증상만 고치는 데 그치지 않고 관련 경계도 확인할 수 있습니다.

## 4. 남은 빈칸까지 기록

T0b에서 macOS 전체 실행과 Windows 전체 설치는 확인하지 못했습니다. 검증자는 이 빈칸을 기록한 뒤 작업 결과를 남깁니다. 다음 사람이 그 기록을 보면 이미 확인된 것과 여전히 확인할 것을 구분할 수 있습니다.

두 AI의 역할을 나누는 목적은 책임을 없애는 것이 아닙니다. 구현과 확인을 분리하고, 실패와 미검증을 다음 작업자가 이용할 수 있는 정보로 바꾸는 것입니다.
