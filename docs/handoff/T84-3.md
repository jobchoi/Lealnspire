# T84-3 지시서 — 실제 게임 동작을 학습 기록에 연결 (구현 Codex, 확정·E2E·QC Claude)

브랜치 `feature/T84-learning-history`(T84-1·2 위). 먼저 docs/design/learning-history.md(1-1절 결정, 2절 GPT 원문 1절 이벤트 정의, "T84-1·2 구현 기록" 절), src/model/history.ts·historySummary.ts·ProgressRepository.ts(기록 API), CLAUDE.md를 읽는다. [제안·잠정]. **화면 모양은 바꾸지 않는다**(대시보드는 T84-4·5).

## 구현
1. 컨트롤러가 주입받은 진행 저장소의 기록 API로 이벤트를 남긴다(직접 localStorage 금지). 대상:
   - 퍼즐 방문 시작·종료(스테이지 진입, 목록·홈·다음 스테이지·새로고침/탭 닫기 — 닫기는 가능한 범위에서 `pagehide`/`visibilitychange`, 실패해도 다음 방문 때 열린 방문을 "종료 사유 미상"으로 닫음)
   - 시도 시작(실행 또는 첫 한 단계 — 한 단계를 여러 번 눌러도 한 시도), 실행 결과 계산(변형별·첫 실패 변형·실패 종류·원인 블록), 결과 도달/중단(초기화·재실행·이탈)
   - 코드 변경 요약(편집 횟수·개정 번호·블록 종류별 수 — 클릭 로그 아님), 고치기, 되돌리기
   - 힌트 단계 공개(같은 방문 같은 단계는 한 번), 시범 시작·끝 컷 도달·중도 종료(시범 내부 실행은 시도로 세지 않음)
   - 완료 확정(성공 마지막 프레임에서 — 기존 저장 시점과 동일), 활동 시간 구간(보이는 동안 마지막 조작 후 60초까지, 재생·시범 분리)
   - 예측·보너스는 `activityKind`로 정규 퍼즐과 구분
2. **성능**: 편집·실행 1회당 저장 작업이 T84 이전보다 눈에 띄게 늘지 않게 — 이력 직렬화·용량 계산은 묶어서(예: 결과 도달·방문 종료·일정 간격) 하고, 키 하나 바꿀 때마다 전체 키 크기를 다시 재지 않는다. 단위 테스트에 "편집 100회 동안 setItem 횟수 상한" 같은 계약을 넣는다. 특히 지금 `ProgressRepository.persist()`는 진행 저장(편집마다 `saveProgram`)에도 이력 `compactHistory`와 이력 전체 `JSON.stringify`를 두 번 수행한다 — 이력이 커지면(최대 2MB) 편집마다 느려지므로, 진행 쓰기와 이력 쓰기를 분리하고 이력 정리는 이력을 쓸 때만, 용량 계산은 캐시한 크기로.
3. 기록 실패(저장 불가)는 플레이를 막지 않고 T78 안내 계약을 따른다. 기록 때문에 실행·재생 타이밍이 바뀌지 않게(동기 저장이 무거우면 묶어서 저장 — 프레임마다 저장 금지).
4. 단위 테스트(컨트롤러): 대표 흐름의 기대 이벤트 순서 — 실패 3회 → 힌트 1·2 → 고치기 → 성공, 한 단계 연타 = 한 시도, 재생 중 초기화 = 중단, 결과 전 이탈 = 완료 아님, 시범 = 시도 아님, 새로고침 뒤 열린 방문 닫힘, 저장 불가에서도 플레이 계속. 집계(`summarizeHistory`)로 시도 수·힌트 사용·살펴볼 퍼즐이 기대와 같음.
