# T51 지시서 — 논리 조건 Model·저장·6단원 맵 탐색 (구현 Codex, 설계·QC Claude)

브랜치 `feature/T51-logic`(v1.5.1 위). 먼저 docs/design/unit6-logic.md(이번 설계), docs/handoff/T47.md(직전 Model 작업 형식), docs/PROJECT_MAP.md, CLAUDE.md, src/model/unit5.test.ts(상태 변환 전수 탐색 방식)를 읽는다. [제안·잠정]. **Model·저장·맵 탐색만**(화면·스테이지 등록은 T52).

## 설계 (Claude 확정, 자세한 내용은 unit6-logic.md 2절)
1. 타입: `Sensor = 'blockedAhead' | 'blockedLeft' | 'blockedRight'`, `LogicTerm = { sensor: Sensor; not?: true }`, `Logic = { terms: [LogicTerm] } | { terms: [LogicTerm, LogicTerm]; op: 'and' | 'or' }`. `if`·`while` 블록에 선택 `logic?: Logic`. `Stage.logic?: true`.
2. 실행: `logic`이 있으면 두 항을 모두 평가(not 적용 후 and/or)한 값으로 판정. 없으면 기존 그대로. 검사 단계·프레임 수는 기존과 같음(1단계, check 프레임 1개). `check`에 `logic?: { terms: { sensor, not: boolean, sensed: boolean, value: boolean }[]; op?: 'and' | 'or' }`를 추가(최종 값은 기존 `result`). 왼·오른 센서는 로봇 방향 기준, 판정 규칙은 앞과 같음(벽·맵 밖 = 막힘). interpreter의 exhaustive switch 유지.
3. 편집 도우미(Model, 되돌리기와 함께 동작하는 기존 편집 방식 따름): 항 센서 바꾸기, 항 not 켜기/끄기, 둘째 항 추가(연산자 지정, 기본 센서 `blockedRight`), 둘째 항 지우기, 연산자 바꾸기(and↔or). `logic: true` 스테이지에서 새로 만드는 if는 `{ terms: [{ sensor: 'blockedAhead' }] }`, while은 `{ terms: [{ sensor: 'blockedAhead', not: true }] }`를 갖게 하는 생성 옵션. 블록 수는 바뀌지 않음.
4. 저장: v2 그대로. 검증 확장 — `logic`은 허용 옵션이 켜진 스테이지에서만, 항 1~2개, 항이 2개일 때만 op, 센서 허용 목록, `not`은 `true`이거나 없음, 알 수 없는 키 거부. 허용되지 않은 스테이지에 `logic`이 든 코드는 기존 단원별 팔레트 위반과 같은 방식으로 그 스테이지 코드만 비움(완료·별 유지). 옛 버전 롤백 영향은 Claude가 CHANGELOG에 적음.

## 맵 탐색 (보고가 핵심)
6단원 스테이지 후보를 찾아 `src/model/unit6.test.ts`에 **후보 맵 상수 + 정답 실행 + 전수 탐색 증명**으로 넣는다(스테이지 등록은 하지 않음). 공통 조건: 출발 방향 E, 변형 2~3개, 맵 6×6 이하, 정답이 모든 변형에서 성공, 정답이 각 변형의 통행 칸을 모두 방문(장식용 빈 칸 없음), 아이가 말로 설명할 수 있는 정답(예: "앞이 열려 있고 오른쪽이 막혀 있으면 앞으로").
- **u6-2(옆 센서)**: unit6-logic.md 3절 맵 초안과 정답 `while [왼쪽 막힘] [F], L, while [not 앞 막힘] [F]`(5블록)을 검증하고, **앞 센서만**(if 앞 막힘 + else, while 앞 열림, repeat 2~10, 앞·왼·오)으로 ≤ 5블록 동시 성공 불가를 증명. 안 되면 맵을 고쳐 보고.
- **u6-3(`and`)**, **u6-4(`or`)**: 정답에 and(또는 or) 조건이 정확히 하나 들어가는 짧은 프로그램(≤ 6블록)과 맵을 찾는다. 원리: 식은 블록 수에 안 들어가므로 `if A and B [X] else [Y]`가 중첩 if보다 짧다. **한 항 조건만**(센서 3개 × not 유무, if/else·while·repeat 2~10 임의 중첩, 앞·왼·오)으로 상한 이하 동시 성공이 없음을 상태 변환 전수 탐색으로 증명. 맵 생성은 테스트 밖 일회성 탐색으로 해도 되고, 찾은 맵만 테스트에 상수로 넣는다. 탐색 스크립트를 저장소에 남기지 말 것(결과·방법은 unit6-logic.md에 기록).
- 전수 탐색 테스트는 시간 대신 **작업 수 상한**으로 제한(T46 결정: 벽시계 단언 금지), `npm run test` 전체가 지금보다 크게 느려지지 않게(목표: 이 파일 10초 이내).
- 조건에 맞는 후보를 못 찾으면 억지로 만들지 말고 무엇을 시도했고 왜 안 됐는지 보고.

## 테스트 (단위)
항 하나·둘, not, and/or 진리표 네 조합(왼·오른 센서 포함, 네 방향), 맵 밖 판정, check 프레임 내용, while+logic 0회·반복·stepLimit 원인, if+logic+else, logic 없는 if/while 결과 회귀(1~5단원 fixture), 편집 도우미와 되돌리기, 저장 왕복·검증 거부(허용 안 된 스테이지, 항 3개, op 누락/과잉, 알 수 없는 센서, not: false).
