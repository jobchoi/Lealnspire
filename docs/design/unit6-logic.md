# 6단원 논리 결합 `not` / `and` / `or` [제안·잠정]

> Claude 작성(2026-11-25). 근거: 사용자 결정(GAME_DESIGN 11절: 기본 개념 전부, 글자 암기가 아닌 개념), ROADMAP 라운드 3 GPT 행("두 조건의 결과와 최종 결과를 나란히 표시", "and와 or가 같다" 오해, 부작용 없는 조건만). 구현은 T51(Model·저장·맵 탐색) → T52(화면·스테이지) → T53(안정화).

## 1. 배울 것

- 조건은 참/거짓 **값**이고, `not`은 그 값을 뒤집는다. 3단원의 "앞 열림"은 사실 `not 앞 막힘`이다.
- 로봇은 앞뿐 아니라 **왼쪽·오른쪽**도 볼 수 있다(센서가 여러 개면 조건을 묶을 일이 생긴다).
- `and`는 **둘 다** 참일 때만 참, `or`는 **하나라도** 참이면 참. 두 조건의 결과와 최종 결과를 나란히 보여 준다.

## 2. 조건 식 (Model)

- 센서 3개: `blockedAhead`, `blockedLeft`, `blockedRight` — 로봇 기준 앞·왼·오른 한 칸이 벽이거나 맵 밖이면 참. 앞 판정은 기존과 같다.
- 식은 **평평한 최대 두 항**: `{ terms: [Term] | [Term, Term], op?: 'and' | 'or' }`, `Term = { sensor, not?: true }`. 항이 둘이면 `op` 필수, 하나면 없음. 괄호·세 항 이상·`not (A and B)`는 다루지 않는다(아이용 범위, 우선순위 문제를 만들지 않음).
- `if`·`while`에 선택 필드 `logic`. 없으면 지금과 같다(if = 앞 막힘, while = 앞 열림). 있으면 식의 값이 참일 때 몸체를 실행한다. `condition` 문자열은 호환을 위해 그대로 둔다.
- 센서는 부작용이 없으므로 두 항을 **모두 평가**해 보여 준다(단락 평가와 결과가 같음을 문서에 남김).
- 검사는 기존과 같이 1단계·check 프레임 1개. 프레임 `check.logic`에 항별 센서 값·`not` 뒤 값·연산자·최종 값을 싣는다.
- 블록 수: 식은 블록이 아니다(if·while 1개로 셈). 그래서 `if A and B [X] else [Y]`는 중첩 `if A [if B [X] else [Y]] else [Y]`보다 짧다 — 퍼즐 상한은 이 차이를 쓴다.
- 6단원 스테이지는 `logic: true`. 이 표시가 없는 스테이지(1~5단원)는 저장된 `logic`을 거부한다(단원별 유효 팔레트 검증과 같은 방식).
- 6단원에서 새로 놓는 if는 `앞 막힘`, while은 `not 앞 막힘`으로 시작한다(열림 = 막힘이 아님을 처음부터 보이게).

- 흐름: u6-2의 규칙(왼쪽이 열리면 돌기)은 u6-3 맵1에서 왼쪽 막다른 갈래로 들어가 부딪힌다 → "양쪽이 다 열렸을 때만"이 필요(and). u6-4는 같은 갈림길 맵에서 "갈림길까지 가기"를 while로 표현하며 and와 or를 바꿔 본다(드모르간: `not 왼 and not 오`의 반대 = `왼 or 오`).

- 탐색 방법: Codex의 상태 변환 DP(`src/model/unit6.test.ts`)를 저장소 밖 일회성 스크립트로 옮겨, 무작위 나무 맵(성과 없음)과 "곧은 통로 + 옆 갈래" 맵군·손 설계 맵을 검사했다. 무작위 나무 맵에서 and/or 후보 0개였던 이유: and가 필요하려면 왼쪽만 열림·오른쪽만 열림·양쪽 열림이 한 길에 함께 있어야 한다. 수치: u6-2 앞 센서 ≤4 변환 1,466개·작업 12,936회, u6-3 한 항 ≤4 변환 14,334개·작업 129,582회, u6-4 한 항 ≤4 작업 약 13만 회 — 모두 동시 성공 없음. ## 4. 화면 (T52에서 확정)

- if·while 머리의 조건 칩: `[not] [센서 그림] [and/or] [not] [센서 그림]`. 센서 그림은 로봇과 화살표(앞·왼·오) + 벽 무늬. 보이는 라벨은 영어 개념어(`not`, `and`, `or`), 설명·aria는 화면 언어.
- 조건 칩을 누르면 작은 편집 줄: 센서 고르기, `not` 켜기/끄기, 항 추가(`and`/`or`), 연산자 바꾸기, 항 지우기. 모두 44px 이상.
- 검사 순간: 해당 센서 칸에 빛, `앞 막힘 ✓ and 오른쪽 막힘 ✕ → ✕`처럼 항 결과와 최종 결과를 나란히(색만으로 구분하지 않음).

## 5. T51 구현·맵 탐색 결과 (Codex, 2026-11-26) [제안·잠정]

Model·v2 저장 검증과 불변 편집을 구현했다. `check.logic.terms`는 두 항 모두의 sensed/not/value를 기록하며 최종 판정은 기존 `check.result`다. 센서는 부작용이 없어 두 항 평가 결과가 단락 평가와 같다. 기존 검사 단계 수(1)와 프레임 수(1)는 유지한다. 생성 옵션은 `createBlock(program, type, { logic: true })`, `Program.create(type, options)`, `FunctionProgram.create(type, fn, options)`로 전달한다. 화면·스테이지 등록은 하지 않았다.

### 후보 폐기와 실제 엔진 반례

**채택 가능한 u6-2/3/4 후보를 확보하지 못했다.** 아래는 탐색한 후보와 실패 근거이며 “해 없음” 증명이 아니다. T52에서 이 맵들을 그대로 등록하면 안 된다.

- u6-2 원래 초안(3절): `while 왼쪽 막힘 [F], L, while 앞 열림 [F]`는 두 맵 모두 성공하지만 맵1의 (3,2)/(4,2)/(5,2), 맵2의 (5,2)를 방문하지 않는다(좌표 0부터). 앞 센서만으로도 **5블록** `repeat 6 [F, L, if 앞 막힘 [R]]`가 두 맵 모두 성공한다. 따라서 모든 칸 방문과 옆 센서 필수성 모두 실패한다.
- 꼬리를 자른 후보: 맵1 `##G / ##. / S..`, 맵2 `####G / ####. / S....`(출발 E). 모든 칸 방문은 만족하지만 `while 앞 열림 [F], L, while 앞 열림 [F]`(5블록), 더 짧게 `repeat 6 [F, if 앞 막힘 [L]]`(**4블록**)로 두 맵 모두 성공한다.
- and 후보: 위 꼬리 제거 맵에 `while [not 앞 막힘 and 오른쪽 막힘] [F], L, while 앞 열림 [F]`(5블록). 모든 칸 방문·두 맵 성공이지만 첫 통로의 오른쪽은 항상 막혀 있으므로 and가 불필요하다. 위 4블록 반례로 폐기했다.
- or 후보: 같은 맵에 `while [not 앞 막힘 or not 오른쪽 막힘] [F], L, while 앞 열림 [F]`(5블록). 역시 모든 칸 방문·두 맵 성공이지만 첫 통로의 오른쪽이 항상 막혀 두 번째 항이 항상 거짓이다. 같은 4블록 반례로 폐기했다.

### 전수 탐색 범위와 수치

`src/model/unit6.test.ts`는 후보 맵 상수·정답·미방문 칸·반례 실행과 상태 변환 DP를 포함한다. 비도착 통행 칸 × 네 방향 전체를 상태로 두고 성공/실패를 흡수 상태로 둔다. 각 크기에서 F/L/R·순차 조합·repeat 2~10·if/else·while의 임의 중첩과 빈 몸체를 생성한다. 전체 상태 변환이 같은 코드는 최소 크기 대표 하나로 합친다. 단항 조건은 앞 센서만 또는 앞/왼/오 × not 유무다. 앞 열림 if도 if 앞 막힘의 두 가지를 맞바꾼 것과 같으므로 앞 센서 전용 탐색에 포함한다.

무한 while은 실패로 합치고 전역 1000단계·반복 진입 제한은 완화한 의미다. 따라서 성공 부재는 제한 있는 엔진에서도 성립하지만, 발견한 반례는 실제 Interpreter에서 재검증해야 한다. 위 두 반례는 실제 엔진에서도 모두 성공했다. 성공의 최소 블록 수라는 주장은 하지 않는다. 테스트 제한은 후보 검사 **200,000회/탐색**이며 벽시계 단언은 없다. 최종 문법/범위에서 위 수치로 재현된다. 6블록 전체·모든 6×6 맵을 전수 탐색한 것은 아니다. 추가 맵 생성 스크립트는 저장소에 남기지 않았다.

후속 설계에서는 분기 뒤에 남는 통로를 실제 경로로 사용하면서, 단순 벽 따라가기 반례도 차단하는 다른 맵군이 필요하다. 이 작업 결과는 맵 후보 미확보 보고이며 6단원 퍼즐 설계 완료로 처리하지 않는다.
